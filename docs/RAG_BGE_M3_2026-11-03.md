# BGE-M3 真实检索对比（2026-11-03）

2026-11-02 的 `docs/RAG_REAL_EMBEDDING_REPORT.md` 把 BGE-M3 标记为 **BLOCKED**（本机没有该模型，`/v1/embeddings` 返回 404，`ollama pull` 在 55% 中断）。本文件记录解除阻塞后的**真实执行结果**：模型从哪里来、用什么精度、同一套 42 条查询下与 hashing / qwen3-embedding 的对比，以及启用时必须同步改的阈值。

## 1. 结论先行

1. **BGE-M3 可用于本项目的检索链路**：1024 维，经 Ollama 的 OpenAI 兼容 `/v1/embeddings` 调用，42 条固定查询上 hit@1 100%、hit@3 100%、MRR 1.0000、引用有效性 100%。
2. **默认阈值 `KNOWLEDGE_MIN_SCORE=0.15` 在 BGE-M3 下失效**：6 条不可回答查询全部被误答（no-answer 0%）。校准到 **0.42** 后回到 100%。
3. `hybrid_rrf` 在 BGE-M3 下的收益是**跨文档覆盖**（`coverage@3` 50% vs 旧排序 25%），不是 hit@1——hit@1 在三个 provider 上都已打满。
4. 语料仍只有 6 篇合成 SOP / 32 个 chunk，**这组数字证明链路、门禁与校准方法，不是通用检索准确率**。

## 2. 模型从哪里来（为什么不是 `ollama pull`）

`ollama pull bge-m3` 在本机两次中断：下载到 641 MB / 1.2 GB（约 55%）后连接停滞，与本机代理（`HTTP_PROXY=127.0.0.1:8111`）的 fake-IP 重定向有关。改为**手工取 GGUF 再导入**，全程可控、可校验：

| 项目 | 实际值 |
|---|---|
| 来源仓库 | `gpustack/bge-m3-GGUF`（HuggingFace，经 `hf-mirror.com` 镜像） |
| 文件 | `bge-m3-Q8_0.gguf` |
| 大小 | 634,553,760 字节（与镜像 `Content-Length` 逐字节一致，已核对） |
| 本地路径 | `E:\models\bge-m3-Q8_0.gguf` |
| 导入方式 | `ollama create bge-m3 -f Modelfile`（`FROM E:\models\bge-m3-Q8_0.gguf`） |
| Ollama | 0.40.13 |
| 维度 | 1024 |
| 推理位置 | 本机 Ollama，仅访问 `127.0.0.1:11434`，无公网调用 |

选 Q8_0 的原因：embedding 模型对量化比生成模型更敏感，Q8_0 体积 605 MB、相对 f16（1.1 GB）几乎无损，比 Q4_K_M（417 MB）更适合作为评测基线。没有用 qwen3-embedding 冒充 BGE-M3——两者分别报告。

## 3. 结果（同一套 42 条查询、同一组分块、每 provider 独立临时 SQLite）

| provider | 排序 | hit@1 | hit@3 | MRR | nDCG@5 | no-answer | citation | coverage@3 | P50 |
|---|---|---:|---:|---:|---:|---:|---:|---:|---:|
| hashing-v1（min_score 0.15） | weighted | 97.22% | 100% | 0.9815 | 0.9861 | 100% | 100% | 75% | 8.1 ms |
| hashing-v1 | hybrid_rrf | 97.22% | 100% | 0.9815 | 0.9861 | 100% | 100% | 75% | 11.4 ms |
| **bge-m3（min_score 0.42）** | weighted | 100% | 100% | 1.0000 | 1.0000 | 100% | 100% | 25% | 555.7 ms |
| **bge-m3** | hybrid_rrf | 100% | 100% | 1.0000 | 1.0000 | 100% | 100% | **50%** | 518.5 ms |
| qwen3-embedding:0.6b（min_score 0.40） | weighted | 100% | 100% | 1.0000 | 1.0000 | 100% | 100% | 50% | 513.2 ms |
| qwen3-embedding:0.6b | hybrid_rrf | 100% | 100% | 1.0000 | 1.0000 | 100% | 100% | 75% | 590.5 ms |

`rankers` 字段可核对：hashing 下是 `["bm25","confidence"]`，真实 embedding 下是 `["dense","bm25","confidence"]`——稠密路只在 provider 具备排序能力时投票（理由见 `docs/EVALUATION.md` R8 的消融）。

延迟差异是模型本身：BGE-M3 单次查询向量约 500 ms（本机 CPU），hashing 是 0.2 ms。这不是流水线开销。

## 4. 阈值校准（换模型必须重算）

| provider | max(不可回答 top1) | min(可回答 top1) | 建议阈值 | `0.15` 是否可用 |
|---|---:|---:|---:|---|
| hashing-v1 | 0.1402 | 0.1797 | 0.1599 | 可用 |
| **bge-m3** | 0.3418 | 0.4911 | **0.4164**（取 0.42） | **不可用**：no-answer 0% |
| qwen3-embedding:0.6b | 0.3404 | 0.4561 | 0.3982（取 0.40） | **不可用**：no-answer 0% |

`confidence` 是 `0.65·cos + 0.35·lexical + 标题加权` 的**绝对分数**，不同模型的余弦分布整体平移，阈值不跟着走就会同时失去「该答的答」和「不该答的拒」。评测现在直接输出这三行，换模型不再靠猜。

## 5. 在本项目启用 BGE-M3

```bash
# .env（不提交）
KNOWLEDGE_EMBEDDING_PROVIDER=openai
KNOWLEDGE_EMBEDDING_BASE_URL=http://127.0.0.1:11434/v1
KNOWLEDGE_EMBEDDING_MODEL=bge-m3
KNOWLEDGE_EMBEDDING_API_KEY=
KNOWLEDGE_MIN_SCORE=0.42
```

**旧库不会自动升级**：检索按 `embedding_model` 过滤，`data/profitops.db` 里是 hashing 向量，切到 bge-m3 后知识库看起来是空的。两种恢复方式：

- 保留审批/审计历史（推荐，已在本机执行）：`scripts/reindex_knowledge.py` 就地重嵌入全部 active 文档，保留文档 ID、chunk ID、标题与审计记录，只替换向量与 `embedding_model`。运行前先备份数据库。

  ```bash
  cp data/profitops.db data/backup/profitops-pre-bge-m3.db
  .venv/Scripts/python.exe scripts/reindex_knowledge.py --dry-run   # 先看会改什么
  .venv/Scripts/python.exe scripts/reindex_knowledge.py             # chunks_by_model: hashing-v1 -> bge-m3
  ```

  也可以对单篇文档调 `POST /api/knowledge/documents/{id}/reindex`（仅 approver）。脚本默认拒绝把索引重嵌回 hashing，避免误降级。

- 可以丢弃演示数据：删除 `data/profitops.db` 后重启，Seed 会用新 provider 重新入库（会清掉审批与审计历史）。

本机 2026-11-03 实测：`6 documents / 32 chunks` 从 `{'hashing-v1': 32}` 变为 `{'bge-m3': 32}`；随后真实 API 检索返回 `rankers=["dense","bm25","confidence"]`、相关查询 `no_answer=false`、无关查询 `no_answer=true`。

切换后建议立刻跑一次评测确认阈值：

```bash
.venv/Scripts/python.exe backend/evals/rag.py --embedding-provider openai \
    --embedding-model bge-m3 --min-score 0.42 \
    --json backend/evals/reports/rag-bge-m3.json
```

## 6. 不能陈述的事

- 不能把 hit@1 100% 说成「BGE-M3 检索准确率 100%」：只有 6 篇 SOP、32 个 chunk、42 条查询，且查询是同一批合成 SOP 的中文改写。
- 不能据此宣称 BGE-M3 优于 qwen3-embedding：两者都打满，差异只在 `coverage@3`，且样本只有 4 条 cross_doc 查询。
- 没有 reranker、没有向量数据库、没有文档级 ACL、没有 PDF/OCR；跨文档覆盖 50% 说明「一个查询要两篇 SOP 才能答全」这件事仍未解决。
- 500 ms 的查询延迟是 CPU 推理结果，未做批处理、缓存或 GPU 对比。
