# ProfitOps AI 面试讲解与高频追问

## 1. 一句话定位

ProfitOps AI 是一个跨境电商利润经营决策 Agent：它从真实经营账本做确定性利润计算，定位利润变化的会计贡献项，核验证据后生成建议，必须经人工审批，才在事务中执行**受控模拟**，并留下可追踪的审计记录。

## 2. 30 秒版本

> 很多跨境团队能看到销售额上涨，却说不清利润为什么下降。ProfitOps 把订单、广告、履约、平台费等账本统一成整数美分的利润桥，用 LangGraph 组织“读取 → 计算 → 归因 → 证据校验 → 建议 → 等待审批”的有状态流程。数字全部由确定性工具计算，Agent 不编数字；建议必须由审批人批准，执行只写模拟记录，幂等键保证重复请求不会产生第二次副作用，审计日志可以按请求 ID 追完整条链路。

## 3. 3 分钟演示脚本

启动：`python scripts/dev.py`，打开 <http://127.0.0.1:5180>。

1. **经营总览（20 秒）**：指出销售额环比上涨、净利润环比下降；利润变动归因第一项是广告支出；底部“贡献项合计与利润变化一致”。点开趋势图的数据表，说明图表和表格同源。
2. **启动 Agent（30 秒）**：点击“启动 Profit Agent”，工作台逐步出现 7 个步骤：读取经营数据 → 计算利润与环比 → 分析异常与贡献项 → 验证证据与完整性 → 创建待审批建议 → 等待人工审批。强调每步有耗时、摘要和请求 ID，状态写入数据库。
3. **查看建议（30 秒）**：点击“查看经营建议”。展示问题、统计周期、8 项证据、条件性影响情景、风险、假设、待补充信息；指出“待执行的模拟动作”展示目标 SKU、参考日预算、模拟新预算。
4. **越权拦截（20 秒）**：当前是分析师，页面没有批准按钮；用分析师 token 直接调 `/approve` 返回 403（可用 curl 现场演示）。右上角切换“审批负责人”。
5. **审批与模拟执行（30 秒）**：填写审批意见，批准；点击“模拟执行已批准动作”。结果显示 `SIMULATION`、预算前后对比、外部调用 0 次、唯一执行记录已保存。
6. **幂等（20 秒）**：点击“再次请求 · 验证幂等”。返回同一执行 ID，提示命中幂等；数据库没有第二条 execution。
7. **审计（20 秒）**：打开审计日志，在“请求 ID”输入框填入刚才执行请求的 ID，精确过滤出开始执行、成功执行、重复回放等事件。
8. **拒绝分支（20 秒，可选）**：再启动一次分析，在审批中心填写原因并拒绝；建议进入终态，不能再批准或执行。

现场可验证的三个证据：

- 利润归因 8 项贡献之和 = 净利润变化（页面底部有核对标记）。
- 分析师 token 调批准接口 = 403，`X-Role: approver` 无效。
- 连续两次执行 = 同一 execution ID，第二次 `replayed=true`，数据库只有一条执行记录。

## 4. 架构图（口述版）

```
React 工作台
   │ 真实 HTTP（Bearer 演示身份）
   ▼
FastAPI ── 统一错误 / 请求 ID / 审计
   │
   ├── 确定性指标层：整数美分利润、环比、8 项贡献桥、数据完整性
   ├── LangGraph 分析图：7 个持久化步骤，等待审批是业务暂停点
   ├── LangGraph 执行图：3 个步骤，事务内幂等模拟
   ├── Tool Registry：6 个工具，Pydantic Schema + 角色 + safe/ask/deny 策略
   └── SQLAlchemy → SQLite（默认）/ PostgreSQL（Compose）
```

## 5. 关键技术决策与“为什么”

### 为什么利润必须由确定性代码计算？

LLM 擅长解释和归纳，不擅长保证算术一致。这个项目的核心承诺是“每个数字都能回算到账本”，所以金额、环比、贡献桥全部由 Python/SQL 计算，Agent 只调用工具、组织流程和生成结构化建议。这样同一份数据每次得到同样的结论，也方便测试和审计。

### 为什么用 LangGraph，而不是一串函数调用？

因为流程有状态、有暂停点、有失败恢复：

- 每个节点把步骤和状态快照写入数据库；`wait_for_approval` 是真实的业务暂停点，不是内存等待。
- 审批后从数据库快照进入执行图，不重跑建议生成。
- 失败节点保留错误码和失败步骤；重启把遗留 `queued/running` 标记为 `restart_interrupted`。
- 图结构让“读取 → 计算 → 归因 → 证据校验 → 建议”的顺序和条件分支可读、可测。

### 为什么用 Tool Registry？

统一管理工具的名称、描述、输入/输出 Schema、允许角色、副作用和策略。Agent 不直接碰数据库或外部系统，只能通过注册过的工具；工具在调用前做 Pydantic 校验和角色校验，未知工具和 `deny` 工具直接拒绝。这样“Agent 能做什么”是显式清单，不是散落在代码里的隐式能力。

### 为什么金额用整数美分？

浮点数会出现 `0.1 + 0.2 != 0.3` 这类误差；利润、折扣、退款、平台费需要精确对账。数据库和 API 全部用整数美分，前端只在展示时除以 100。利润率和环比用 `Decimal` 四舍五入到两位，分母为 0 返回 `null`，不伪造 0%。

### 退款和采购成本会不会重复扣？

不会。退款只作为负向收入扣减销售额；采购成本字段已经是退货后的残值，不再对退款重复扣成本。这个口径写在 `docs/CONTRACT.md`，测试覆盖了退款压力和负净销售额边界。

### 利润桥怎么验证？

8 项贡献：销售额贡献 `current - previous`，其余成本项贡献 `-(current - previous)`。八项之和必须等于净利润变化；`verify_evidence` 会重算并比对，`bridge_verified` 在 API 和 UI 中可见。归因是会计贡献项，不是因果证明，文案里明确写了这一点。

### 数据不完整怎么办？

每日经营记录按“店铺 × SKU × 日期”检查覆盖；缺行或 `complete=false` 会产生具体缺失项。Agent 在 `verify_evidence` 阶段停止，状态 `insufficient_data`，不创建建议。空集不等于“零销售”，不会把缺失值当零。

### 如何保证审批不会被绕过？

三层：

1. 服务端 Bearer token 映射角色，客户端传 `X-Role` / `X-Actor` 无效。
2. 审批和执行都要求 approver 角色；Tool Registry 和业务服务双层校验。
3. 状态机用条件 UPDATE 抢占：`WHERE id=? AND status='pending_approval'` / `status='approved'`；rowcount 不等于 1 就拒绝。审批结果不可反转。

### 幂等和并发怎么保证 exactly once？

- 分析请求键全局唯一，重复请求返回原分析；键绑定请求内容和创建者，不一致返回 409。
- 执行键全局唯一，`executions.recommendation_id` 也唯一。
- 执行先抢占建议状态（`approved → executing`），再插入唯一执行记录，最后在同一事务里写模拟结果、更新状态和审计。
- SQLite 下执行入口先 `BEGIN IMMEDIATE` 获取写锁；PostgreSQL 下条件 UPDATE 自带行锁。竞争事务等待后重新求值，看到状态已变，返回已有 execution 并标记 `replayed=true`。
- 测试用 6 个线程同时执行同一建议，断言 6 个响应同一 execution ID、只有 1 个非回放、数据库只有 1 条执行记录和 1 条成功审计。

### 为什么不用 `SELECT ... FOR UPDATE`？

条件 UPDATE 本身就是原子的“检查并抢占”，少一次查询，也避免“先读后写”的竞态。SQLite 没有行级 `FOR UPDATE`，条件 UPDATE + `BEGIN IMMEDIATE` 是跨两种数据库都能工作的方案。

### 执行失败了怎么办？

模拟器抛异常时，执行记录写 `execution_failed`，保存错误码和消息，建议进入终态，审计记录 failure，HTTP 返回 500；重复请求返回同一条失败记录并标记 `replayed=true`。失败可见，不伪装成成功。

### 审计日志可信吗？

每条审计记录包含 actor、action、object_type、object_id、request_id、outcome、details 和时间。审批、执行、回放、失败、被拒绝的请求都会记录；审计与业务写在同一事务里（拒绝请求用独立事务补记）。当前是应用级审计，生产还需要防篡改存储、日志外送和权限控制。

### 为什么默认 SQLite，Compose 用 PostgreSQL？

SQLite 让演示无需外部服务、一条命令可复现；WAL、外键、30 秒 busy timeout 足以支撑单机演示。Compose 提供 PostgreSQL 16 + 持久卷，事实模型、唯一约束和条件 UPDATE 在两者通用。需要诚实说明：本机 Docker 引擎不可用，PostgreSQL 容器路径未实测，只有 SQLite 并发测试通过。

### 为什么不用微服务？

这是 MVP，业务闭环的复杂度在状态机、证据和审计，不在服务拆分。模块化单体让事务边界清晰（审批、执行、审计在同一数据库事务），也避免分布式事务和跨服务幂等。等出现独立扩缩容、团队边界或数据隔离需求，再按边界拆。

### 如何接入真实 LLM？

把“解释与文案”抽象成 `ExplanationProvider`：默认规则实现，可选 LLM 实现。LLM 只接收工具算好的结构化指标，输出解释、风险和建议草稿；数字仍由确定性工具产生，建议仍要经过证据校验和人工审批。评测可以用固定案例比较关键结论、证据引用和是否越权承诺收益。

### 如何扩展到生产身份和多租户？

接入 OIDC，服务端从 token 解析 tenant/role；所有查询按 tenant 过滤；审批和执行增加 tenant 条件；审计记录 tenant；密钥走 Secret Manager；加限流、请求体大小限制、CORS 和安全响应头；数据库迁移用 Alembic。

### 为什么分析用 BackgroundTasks？生产怎么办？

MVP 用 FastAPI BackgroundTasks 是为了零额外基础设施，HTTP 立即返回 202，前端轮询分析状态。生产应换成持久化队列 + worker，保留现有的状态机、步骤快照和 `restart_interrupted` 语义；多 worker 下还要考虑任务去重和租约。

### 这个项目最大的局限是什么？

四个：演示认证不是生产安全方案；规则引擎不是 LLM，不会生成开放式策略；Docker/PostgreSQL 容器路径未实测；没有增量迁移和持久化队列。项目文档明确标注了这些边界，不把 MVP 说成生产能力。

## 6. 高频追问速答

**Q：销售额上涨、利润下降，一定是广告的问题吗？**
A：不一定。利润桥只能说明“哪个会计贡献项吃掉了利润”，不能证明因果。页面和文案都写的是“会计贡献项”，建议也是条件性情景，要求补充活动级 ROAS、边际获客成本等证据。

**Q：为什么主要驱动选广告支出？**
A：按负向贡献排序，广告支出是最大负向项。规则引擎不会凭空选择；`analyze_drivers` 对 8 项贡献排序，测试样本覆盖广告、履约、退款等不同驱动。

**Q：建议里的利润改善数字是怎么来的？**
A：条件性情景：以本周期日均广告花费为参考预算，假设下调 15%、预算完全用尽、收入和其他成本不变，节省额兑现 50%–100%。这是明确标注的情景测算，不是收益承诺，也不是广告弹性估计。

**Q：如果审批人批准了但执行时数据已经变了？**
A：执行读取的是建议创建时的数据库快照和动作参数，不重新计算；状态机只允许 `approved` 执行。数据变化不会改变已批准动作，但会在下一次分析中体现。生产可以加“建议有效期/重新验证”策略。

**Q：为什么审批意见必填？**
A：审批是责任行为，意见进入审计，便于复盘。API 约束 2–500 字，前端同样禁用过短意见。

**Q：拒绝后还能恢复吗？**
A：不能。`rejected` 是终态，审批结果不可反转；要重新处理就发起新分析。这是有意的审计设计。

**Q：为什么执行接口返回 500 而不是 200？**
A：模拟失败是执行失败，不能伪装成成功；HTTP 500 表示服务端执行失败，响应体保留 execution 记录和错误诊断。重复请求仍返回同一条失败记录并标记 `replayed=true`。这是契约中的明确选择。

**Q：如何防止重复点击“启动分析”？**
A：前端按钮在请求中禁用；API 支持 `Idempotency-Key`，同一键重复请求返回原分析。前端每次点击生成新的 UUID，所以“重复点击”会产生新分析；如果要严格防重，可以复用同一个键或加业务去重键。

**Q：审计能按请求 ID 查吗？**
A：可以。`GET /api/audit-logs?request_id=...` 精确过滤，前端审计页有输入框；也支持 `object_id` 查某个建议的全链路。

**Q：为什么时间戳带 Z？**
A：数据库驱动对时区的处理不一致（SQLite 常返回 naive datetime）。API 统一输出 UTC ISO 8601 带 `Z`，前端按 UTC 解析后本地化显示，避免“看起来是 UTC、实际按本地时间解析”的偏差。

**Q：工具策略 safe/ask/deny 具体怎么落地？**
A：`/api/tools` 暴露每个工具的策略；`safe` 是只读/纯计算/仅写本系统提案，`ask` 是必须审批后执行的模拟动作，`deny` 在注册表调用前直接拒绝。当前唯一 `ask` 工具是模拟执行，受 approver 角色、`approved` 条件 UPDATE 和唯一执行记录三重约束；没有注册任何 `deny` 工具。

**Q：为什么测试数从 29 变成 33？**
A：接管后补了 4 个回归：工具 policy/deny、API UTC 时间戳、审计 request_id 过滤、Seed 不删除审批/执行/审计。前端补了动作预览与审计过滤测试，从 5 变 6。

**Q：Docker 没跑过，怎么证明能启动？**
A：不能证明。只能证明 `docker compose config` 语法通过、Dockerfile 和依赖锁文件齐全、SQLite 路径完整跑通。面试时主动说明这是环境阻碍，并给出在 Docker 可用机器上的验证命令；不要把“配置存在”说成“容器已运行”。

**Q：如果让你继续做两周，你先做什么？**
A：Git 基线已建立；下一步在 Docker 可用环境跑通 Compose 并补验证记录；然后 Alembic 迁移、持久化队列、OIDC/多租户、限流；最后抽象 LLM Provider 和第二种演示场景。顺序是先补交付风险，再补生产能力，最后扩 Agent 能力。

## 7. 讲解时的边界清单

不要声称：

- “已经接入真实广告/采购/支付系统”——所有执行都是 simulation。
- “已经接入 MCP”——没有实现。
- “用了 LLM 做利润计算”——数字是确定性代码算的。
- “Docker/PostgreSQL 已验证”——只验证了配置语法。
- “生产级认证/多租户”——当前是公开演示 token。
- “归因证明了因果”——只是会计贡献项。
- “预期影响是收益承诺”——是条件性情景。

可以强调：

- 数字可回算、证据可校验、数据不足会停止。
- 审批不可绕过、执行幂等、失败可见。
- 审计可按请求 ID 追踪。
- 测试真实执行，没有跳过。
